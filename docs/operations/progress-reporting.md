# 現況更新と進捗報告

## 正本と優先順

現在の進捗の入口は[`dots-current-status.json`](dots-current-status.json)。製品要件・完成条件はmaster planを維持する。旧task表・診断表・日付付き計画は履歴であり、現況一覧に反する未完了欄を現在の故障として再報告しない。
利用者の最新指示と、対象・版・検査範囲が一致する新しい実証を優先する。日付が新しいだけの別環境の成功を、以前の不具合の解消へ流用しない。

## 報告前の必須照合

1. 現況一覧を読み、Git/PRで正式版の版を確認。稼働場所はサービス設定、Git差分、配信元を読み取りで確認する。秘密値・環境ファイル本文は出力しない。
2. 状態を4軸で分ける: 実装、検証、main反映、稼働反映。「未統合」「未確認」は「未修正」「故障中」ではない。
3. 未解決と報告する候補ごとに、後の成功記録、同じ不具合か、検査条件、反映先を照合。現在の再現証拠がない故障を修正予定へ戻さない。記録が古い・不一致なら「未照合」と説明し、状態を推測で失敗へ変えない。
4. `python scripts/validate_progress_status.py`を実行し、同じ検査範囲の最新結果と状態の矛盾がないことを確認する。機械検査は実施・能力・製品完成の証明ではない。
5. 利用者へは、使えるもの、未反映の成果、未確認の操作、次の作業を分けて日常語で報告する。

## 更新のタイミング

- 検査の受入、PR統合、稼働反映、利用者試験結果、再現した回帰の各節目で、次の作業や最終報告の前に更新する。
- 項目はID、目的、4軸、次の一手、検査範囲、結果・記録時刻・根拠を持つ。未確認は根拠なしでもよいが、成功は同範囲の実証なしに記録しない。
- 稼働中の未コミット変更には`working_tree`、異なる部分が混在する場合は`mixed`。main統合は稼働反映を自動的に意味しない。
- `baseline_main`は照合時の基準版であり、この一覧を追加したcommit自身のSHAではない。文書更新だけのmergeで自己参照SHA更新PRを作らない。
- 記録時刻は試験実行時刻と区別する。過去の受入記録を読んだだけなら、今回再実行したと表現しない。
- 同じ範囲で新しい失敗が再現した場合だけ、根拠を追加して修正へ戻す。既存速度比較・復元・調査を進捗整理だけのために反復しない。
- 独立レビューの指摘が未解消なら、完了や統合済みと記録しない。CI待ちを製品の実装失敗と混同しない。

## 会話と旧規約

通常のDots作業は現在の一会話を窓口とする。利用者向けの別会話作成、アーカイブ会話の復帰・起動は利用者の明示指示なしに行わない。内部サブエージェントへの限定委譲と利用者向け別会話を区別する。
旧部門間の起動・通知・割当規約は、利用者が部門別の複数会話運用を明示再開した場合だけ適用する。通常は同一会話内で計画・独立レビュー・Git反映を閉じ、架空の受領待ちや自己通知を作らない。

## 初期一覧の証拠範囲

2026-09-27に主会話の保存済み履歴、稼働版の記録、main #292、正本プラグインAPIを照合して初期一覧を作成した。`local:`は未配送の稼働作業場所の証拠。これをmain版での成功と拡張しない。原証拠が失われた場合は未照合とし、新しい失敗と扱わない。
