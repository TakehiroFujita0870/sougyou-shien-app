# 調査済み概要の保存失敗修正

## 再現と原因

2026-09-27、許諾された通常保存先の架空データ試験で、出典・根拠・調査Runは保存できたが、概要保存が503になった。ロールバック専用の実DB診断で、Neo4jのRecordはMappingでありながら反復時には列名ではなく値を返すことを確認した。既存デコーダーの `set(record)` による列集合照合が、正しい5列の結果を拒否していた。

## 変更と受け入れ条件

- Mappingの列名を `record.keys()` で照合する。5列の完全一致、所有者、ID、型、revision、JSONの検査は維持する。
- 実ドライバーのRecordを用いる回帰テストを先行追加して失敗を再現し、修正後に成功させる。
- 列不足・未知の列は引き続き拒否する。保存データの補完や認証条件の緩和をしない。
- 正式版反映後、同じ架空データの概要保存・根拠取得を確認する。新しい外部調査や実データ削除は行わない。

## 検査と影響

修正前は実Record回帰テストが失敗、修正後のデコーダー検査は37件成功。実DB診断は必ずロールバックし、概要と保存受付の記録が残らないことを読み戻した。実サービスでの保存成功は反映後の別証拠として扱う。

DB移行、依存変更、UI変更はない。コードの巻戻しは可能だが、旧版へ戻すと同じ正常なRunの概要保存が再び拒否される。
