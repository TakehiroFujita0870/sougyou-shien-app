# Dots. UI改善・内部整理の並走計画

## 要望 / ゴール / 成功指標

要望原文: 「利用者から見える結果・安全性・性能を維持できれば、内部構成や手順の変更は許容します」「UI改善とリファクタリングの並走計画をドキュメント化し、ゴール設定できるような状態にしてください」。

ゴール: PCのDots.を読みやすくコンパクトにし、UIでアイデア・アセットを削除できるようにする。同時に、既存の保存・検索・根拠追跡・本人限定接続を維持したまま内部の責務と依存を整理し、以後の変更を独立して検証できる状態にする。

成功指標: 下記USの全条件、影響範囲の既存検査、1280×720の横断監査、正式版への統合と稼働反映が完了する。行数削減や分割ファイル数は成功指標にしない。

利用者が本書のゴールを開始したため実装を進める。本書の実行はMVPの再実装・再調査を意味しない。

追加要望: 「冗長すぎるドキュメントとか、過去資産の残骸ありませんか。リファクタリング対象に含めてほしい」。US-1〜6の完了は維持し、文書と旧資産の整理をUS-7として追加する。追加部分は計画済み・未実装であり、前回の検証を取り消さない。

## ユーザーストーリーと受け入れ条件

### US-1 一覧を読みやすくする

As a Dots.利用者, I want 一覧と画面移動を小さく読みやすくしたい, so that 内容へ目を向けられる。

Given: 1280×720のPC画面でホームを表示する。
When: 3タブと3画面を切り替え、長い日本語のカードも見る。
Then: タブに同一線幅の電球・カード・人のつながりのアイコンがあり、サイドバーは幅192px、ナビ文字14px・アイコン18px・行高40pxを基準にする。カード題名16px、本文14px、補足12pxを共通尺度とし、意味による強調を除きページ間で揃う。切れた本文は詳細で読める。星空と正式ロゴを維持し、通常文字は背景とのコントラスト比4.5:1以上、操作部品の識別は3:1以上にする。

### US-2 調査状況を一覧で識別する

As a Dots.利用者, I want 題名のそばで調査状況を知りたい, so that 次に検討する案を選べる。

Given: 未調査・正式調査済み・過去調査取り込みのアイデアがある。
When: 一覧を表示する。
Then: 題名横の小さいバッジで既存の状態を区別する。過去調査を実行済みResearchRunと偽らず「過去調査あり」と表示する。長い題名でもバッジが見える。色だけに意味を依存せず、選択状態は枠と背景でも分かる。

### US-3 UIから可逆削除する

As a Dots.利用者, I want 不要なアイデア・アセットを画面から消したい, so that 一覧を整理できる。

Given: 本人の現行記録とその根拠・関係がある。
When: カードのゴミ箱を押して対象名を確認して削除し、後でサービス管理の削除済み一覧から復元する。
Then: 記録は通常一覧・検索・グラフで非表示になり、依存する関係は現行として利用されない。他の記録・共通出典は消えず、履歴と根拠は保持する。復元後は既存の現行判定を満たす内容だけ戻る。再送は重複処理せず、他の更新との競合は拒否して再読込みを促す。ChatGPTへ削除・復元ツールを追加しない。

### US-4 アセットを小さな操作で編集する

As a Dots.利用者, I want 各アセットの題名と内容を直接編集したい, so that 会話を経ずに訂正できる。

Given: カテゴリーなしの共通アセット一覧がある。
When: 右上のペンで編集・保存・キャンセルをする。
Then: アイデアと同じ文字尺度で表示し、右上のペンとゴミ箱は見た目16px、操作範囲32×32px以上とする。操作に日本語の説明名とキーボードフォーカスがある。保存失敗では入力が残り、共有範囲・改訂履歴・再送防止・競合処理を維持する。自己紹介専用欄とカテゴリーは作らない。

### US-5 内部整理で既存結果を維持する

As a Dots.利用者, I want 内部を整理しても既存記録を同じように使いたい, so that 改善中も安心して利用できる。

Given: 下書き、8観点の正式概要、出典URL、根拠付き関係、訂正履歴、非共有情報の既存fixtureがある。
When: 同じ保存・取得・検索・訂正を内部整理後に行う。
Then: 返却内容・順位と同点順・拒否条件・共有制限・履歴の現行判定・再送結果が維持される。取引の分割や接続回数の増加、検索候補数・モデル・索引・タイムアウトの変更をしない。結果が意図的に変わるのはUS-1〜4の表示と削除操作だけ。

### US-6 グラフとサービスを維持する

As a Dots.利用者, I want ページ移動と起動停止が引き続き使える, so that 内部整理が日常利用を妨げない。

Given: 3画面と奥行き・物理演算を持つグラフがある。
When: グラフを操作して他画面へ移動し、戻る。サービス状態を表示し既存の開始・停止経路を検査する。
Then: 白画面、残存描画ループ、重複イベント、終了後の状態更新がない。グラフの実階層と根拠表示を維持する。本人限定・Origin・CSRF・固定起動順・停止順・準備完了判定は変えない。検査だけのために通常DBを停止しない。

### US-7 文書と旧資産を減らす

As a Dots.利用者, I want 現行の説明と必要なプログラムだけを残したい, so that 古い状態の誤読と不要な保守を減らせる。

Given: 現行の3画面・MCP・保存検索と、過去の計画・旧画面・検査・運用手順が同じリポジトリにある。
When: 参照先、実際の起動入口、検査、データ復旧との関係を確認して整理する。
Then: 重複する説明は正本へ集約し、古い現況説明・完了済み作業だけの文書は参照を付け替えて削除する。残す契約・安全規則・復旧手順は欠落させない。現行で使われない旧機能は専用検査・Story・手順・依存も同じ目的単位で整理し、通常のビルド・検査に残さない。現行の3画面、MCP、保存検索、根拠、共有制約、起動停止の結果は維持する。保存済みデータ・localStorage・認証情報は消さない。Gitで取り戻せる資料を別の保管フォルダーへ大量に移すだけの整理はしない。

## 質問リスト

現時点で利用者の追加判断は不要。削除は物理削除ではなく復元可能な非表示に固定する。実装で外部契約の変更や既存データ移行が不可避と判明した場合だけ、その範囲を止めて選択肢を提示する。

## スコープ外

- モバイルUI、別解像度監査、人的ネットワークの本実装。
- グラフの新しい見た目、検索順位改善、モデル更新、ベンチマークの反復。
- 新規外部調査、Deep Researchの再実行、接続登録・鍵交換、再起動の反復。
- Neo4jの置換、DB移行、既存データの物理削除、ChatGPTの削除ツール。
- 参照と起動経路を確認しない旧機能の一括削除。依存ライブラリの更新はしないが、廃止した機能だけが使う依存の除去とロック同期はUS-7に含める。
- `docs/inherited/`の継承元・サブモジュールの変更、保存済みデータ・認証情報の削除。
- 独自の通知・ジョブ基盤、別の利用者向けCodexタスク、別アプリ化。

## 実行順と並走の境界

1. P0で現況と不変条件を確認する。UI監査スキルを実装前に読み、既存検査の不足部分だけ追加する。
2. UI担当はU1→U2、内部整理担当はR1→R2、第三の担当はD0→D1を独立して進める。
3. D1のHTTP契約が確定した後、UI担当がU3をfixtureで先行実装できる。実通信の受入はD1統合後に行う。API所有者と画面所有者は同じファイルを編集しない。
4. UIの共通尺度が単独検査とrootレビューを通り意味単位commitになった後、R3が現行入口を分離する。`App.jsx`と共通スタイルはこの間R3だけが所有する。U3は局所画面だけを並走できる。
5. R4がグラフ内部を整理する間、グラフ画面の見た目変更をしない。
6. 最後にV1の横断確認と正式版・稼働反映を行い終了する。

追加US-7はC0→C1/C2→C3の順。文書とコードは非重複の所有範囲で並走できるが、旧入口の利用状況を確認する前にコードを消さない。追加作業の状態は下表で管理し、完了済みV1を未着手に戻さない。

最大3つの内部作業を並走させるが、依存と所有権を優先する。根拠のない最大並列化や待機中の新タスク作成は禁止。rootは割当・検査・独立レビュー・統合を担う。内部worker/reviewerは利用者の更新したゴール指定どおりGPT-6 Luna / High。新しい利用者向け会話は作らない。

## 維持する契約と検証方法

P0確認: 正式版と稼働版の製品コードに差はなく、差分は文書・監査指示・プラグインの既配信手順だけ。現況validatorは成功。既存のread/write parity、local client・home・graphの検査を再利用する。PC実画面でサイドバー約248px、アセットの本文下に大きい編集ボタン、アイデア状態の独立行と3画面の尺度差を確認した。ブラウザー倍率を標準へ戻し、DOMの実寸1280×720を確認して監査した。初期グラフは描画初期化中のため、この観測だけで故障扱いにしない。判断待ちIssueは停止閾値未満で、今回のスコープとは独立している。

- 保存: 所有者、改訂照合、再送キー、受付、監査を同一成功条件に保つ。途中成功を作らない。
- 読み取り: 共有許可、出典URL、現行根拠、訂正済み関係、8観点の順と本文、非現行・非共有の拒否を保つ。
- 検索: 候補数、全文とベクトルの合成、再順位付け、同点順、経路の付加を変えない。モデル固定版・次元・オフライン読み込みを保持。
- ローカル: ループバック、Host/Origin/CSRF、固定操作、同一ブラウザーの安全条件を保持。削除経路にも既存保護を適用。
- UI: 既存保存に使う通信、失敗時入力保持、ページ終了時の破棄とabortを保持。
- 性能: 新たな速度比較はしない。問い合わせ数、モデル呼出回数、候補上限、遅延読み込み、接続の寿命を検査で固定する。明確な劣化が判明したらその変更を差し戻す。

変更単位では関係する検査だけ、最終V1で影響範囲の全体検査を一度実行する。同じ版の成功を再実行しない。既存opt-in実Neo4j検査は保存境界を変えるD1/R2に絞り、既存隔離fixtureを使う。再起動・外部調査・スマホ操作を利用者へ求めない。

## 完了・停止・戻し方

- 各目的単位を検査・独立レビューしてcommitし、節目にpush/PR/mainへまとめる。既存必須CIを迂回しない。UI変更と結果維持の内部整理は別commit/PRにする。同じファイルの差分を部分的に取り込む場合は、他の未コミット変更を含まない送出用checkoutで、そのcommit単独の構文・関係検査を確認してからpushする。共同作業中の全体検査だけで単独commitを検証済みとしない。
- 正式版反映だけで稼働完了としない。稼働コードへ安全に反映し、既存稼働サービスのreadyと画面を確認する。DB・鍵・モデル・保存先は触らない。
- 確認で既存不具合が再現した場合のみ根拠を記録する。無関係な不具合は今回の完了条件へ追加しない。
- 契約変更、データ移行、新たな支出・公開が必要なら該当範囲を止め、利用者へ判断材料を返す。他の安全な独立作業は継続する。
- 回帰は該当目的単位のrevertで戻す。削除は履歴を保持するためUI復元が可能。DBを過去のコピーで上書きしない。
- US-1〜6/V1は完了済み。追加US-7はC0〜C3を満たし、未統合・未検証がなければ完了。任意の磨き込みを追加しない。
