# Founder Graph schema v1→v2 変換スパイク

最終更新: 2026-09-22
状態: 実DBへ書き込まない事前検査

## 目的

いまの保存形式を新しい保存形式へ移す前に、「何が移せるか」「何が足りないか」「移した後に同じ意味を保てるか」を合成データで確認する。ここで行うのは一覧と変換結果の下書きだけであり、Neo4j、既存データ、実ユーザーデータには接続しない。

## 使い方

```powershell
$env:PYTHONPATH = 'backend'
python scripts/founder-graph/schema_v2_spike.py --strict --summary
```

引数なしでは、合成会話20件、名刺相当の人物10件、アイデア1件、根拠1件を使う。`--input <JSON>`を指定すれば、旧形式のJSON出力を検査できる。詳細な対応表と指摘一覧が必要な場合は`--summary`を外す。

`--strict`が成功するのは、移行を実行してよいという意味ではない。旧データを本番の保存場所へ書き込む工程は、別の検査で「入力の保存」「件数と本文の照合」「一括書込みの失敗時に元データを残すこと」を確認してから行う。

## この検査が確認すること

- 必須項目の不足。たとえば人物名、所有者、原文、版番号がない行を止める。
- 同じ人物やアイデアを指す行の重複。旧形式に明示的な同一物の印がある場合は、複数の版を一つにまとめる。
- 関係の両端や根拠が存在しない孤立した関係。
- 原文、引用範囲、調査、レポートが参照する親情報の欠落。
- 別の利用者に属する情報を結ぶ関係。
- 旧IDから新IDへの対応表、入力全体のハッシュ、変換後の件数。
- 元に戻すための前提と、変換前後で照合する項目。

## 変換でまだ確定していない点

1. 旧形式に同一人物を示す情報がない場合、名前だけで自動的に同一人物とは決めない。本人確認が必要である。
2. 旧形式に本文の切り出し位置がない場合、引用範囲を新しい形式へ自動生成しない。原文保存後に別工程で作る。
3. 旧形式の直接関係は、新しい形式では根拠、確信度、期限を持つ一件の記録へ変える。旧関係にこれらがなければ、確認済みとは扱わない。
4. このスパイクは変換結果を表示するだけで、Neo4jへの書込み、削除、復元を行わない。

## 元に戻すための前提

- 変換前JSONを読み取り専用で保存する。
- 変換処理は入力を変更しない。
- 入力全体のハッシュ、変換版、旧IDと新IDの対応表を同じ世代で保存する。
- 新しい保存場所への反映は一括で行い、途中で失敗したら新しい書込みを破棄する。
- 元のデータは、移行と再起動後の照合が完了するまで削除しない。

## 次の工程への引き継ぎ

この成果物の次に、実装担当は次を行う。

- 新しい保存形式で、同一物とその版を表す記録を定義する。
- 関係、根拠、原文の引用範囲を保存する記録を定義する。
- 合成データを実Neo4jへ一度だけ投入し、停止・再起動後の件数、ID、根拠、代表検索結果を照合する。
- 失敗時に元データを変更せず再試行できることを確認する。

このスパイクは、上記の実装へ進むための前提を明らかにした。実データ投入の承認や外部送信の承認は要求していない。
