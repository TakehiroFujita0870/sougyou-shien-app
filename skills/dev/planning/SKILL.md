# planning — 要件・仕様・計画

最終検証日: 2026-08-09

## 目的

1行の要望を、実装・検証・レビューが可能な単一の計画文書に変換する。要件、仕様、タスク、設計判断を別文書に分散させない。

## 適用タイミング

- 新機能、変更、修正、技術選定を開始する前。
- implementation から3周ループ後に差し戻されたとき。
- 受け入れ条件、スコープ、または設計判断が変わったとき。

## 手順

1. 要望を原文のまま記録し、ゴールと成功指標を1文ずつ書く。
2. 利用者ごとにユーザーストーリーを `As a <利用者>, I want <行為>, so that <価値>` で記述する。
3. 各ストーリーに、検証可能な受け入れ条件を `Given / When / Then` で1件以上付ける。Then には観測可能な結果だけを書く。
4. 要望中の `など`、`柔軟に`、`いい感じに`、`適切に`、`必要に応じて`、`可能な限り` を検索する。該当箇所は推測で補完せず、決定者・質問・判断期限を持つ質問リストへ移す。回答まで実装タスクを作らない。
5. 「しないこと」をスコープ外リストに列挙する。既存機能の変更、対応プラットフォーム、データ移行、運用対応は明示的に含めるか除外する。
6. 作業を1 PR あたり差分500行以内かつレビュー30分以内を目安に分解する。各タスクには、成果物、完了判定コマンドまたは観測方法、不確実性ラベルを付ける。
7. タスクを `既知`、`類推可能`、`未知` に分類する。未知には、実装前に結論・調査方法・時間上限を明記したスパイクを置く。未知の実装タスクは作らない。
8. 技術・スキーマの選択は同じ計画文書の ADR 節に記録する。選択、理由、却下した選択肢と却下理由、結果を残す。
9. 変更時は、コード変更より先に計画文書を更新する。変更履歴に日時・変更内容・理由を追記し、影響タスクを再分解してから implementation に戻る。差し戻し時は、矛盾した計画箇所も記録する。

## Exit Criteria

- ◎ 全ユーザーストーリーに Given/When/Then の受け入れ条件がある。検査: `rg -n "Given:|When:|Then:" <計画文書>` の件数をストーリー数と照合する。
- ◎ 禁止曖昧語が計画本文にない。検査: `rg -n "など|柔軟に|いい感じに|適切に|必要に応じて|可能な限り" <計画文書>` が0件。ただし質問リストの引用は除く。
- ◎ スコープ外リストがある。検査: `rg -n "^## スコープ外" <計画文書>` が1件以上。
- ◎ 全タスクに完了判定方法と不確実性ラベルがある。検査: タスク表の全行に `既知|類推可能|未知` と `検査:` があることをレビューする。
- ◎ 未知タスクの前にスパイクがある。検査: `未知` 行ごとに先行する `スパイク` 行があることを確認する。
- ◎ ADR に選択と却下案・理由がある。検査: `rg -n "^## ADR|却下" <計画文書>` を確認する。

## アンチパターン

- 「使いやすくする」のように観測できない完了条件で実装を始める。
- 不明点を実装者の推測で決める。
- 未知の技術をスパイクなしで本実装に入れる。
- 仕様変更後も古い計画を残し、コードだけ更新する。

## 成果物様式

```md
# <変更名> 計画
最終検証日: YYYY-MM-DD

## 要望 / ゴール / 成功指標
## ユーザーストーリーと受け入れ条件
### US-1
As a ...
Given: ...
When: ...
Then: ...

## 質問リスト
| ID | 質問 | 決定者 | 期限 |
## スコープ外
- ...
## タスク
| ID | 成果物 | 完了判定（検査:） | 不確実性 |
## ADR
| 判断 | 選択と理由 | 却下案と理由 | 結果 |
## 変更履歴
| 日時 | 変更 | 理由 | 影響タスク |
```

## 良い実行例

要望「申請状況を見たい」に対し、利用者、表示する状態、Given/When/Then、表示しない個人情報、状態取得のスパイクを計画に書く。タスクの完了判定を「該当E2Eテストが通る」とする。

## 悪い実行例

「申請状況をいい感じに一覧表示する」とだけ書いて実装する。禁止曖昧語の検索と受け入れ条件不在により、Exit Criteria の第1・第2項で検出される。
