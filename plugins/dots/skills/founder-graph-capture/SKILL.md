# Dotsへの自然な記録

この手順は、現在のメッセージでDotsが利用可能で、利用者が自分の創業活動について新しい具体的な内容を話した場合に使う。一般論の質問、単なる雑談、第三者の噂だけでは記録を増やさない。Dotsを選んでいないメッセージでDotsへ保存したと主張しない。

1. 新しい具体的なIdeaが会話に出たら、Dots内で同一記録がないか先に確認する。同じ記録があれば重複作成せず既存記録を使い、新規の場合は`capture_idea`で未調査の下書きとして保存する。その後、関連する既存Idea・Asset・Sourceを検索する。類似するだけで同一とは断定しない。既に手元にある資料・能力・経験は`capture_asset`で独立して記録できるが、その場で考えた質問や分析観点を実在Assetとして捏造しない。再試行は同じ内容に同じ重複防止キーを使い、保存済みと伝えるのは書込み結果を受け取った後に限る。
2. 通常用のDotsでは、会話で共有した機微でないIdeaの短い題名・要約を`shareable`にし、会話原文はローカルに留める。人物の連絡先、非公開メモ、資料本文、非公開URLはChatGPTへ返さない。人物・組織・Idea・資料の共有設定は実際に共有可能な内容だけを明示する。架空fixture専用の接続先へ実データを書かない。曖昧な人物統合、削除、共有範囲の拡大には確認を得る。
3. 新規保存または既存記録の再利用で未調査Ideaを扱ったら、既存の会話内で同じIdeaへの調査提案を既に提示または断られていない限り、Dots内の関連Idea・Asset・Sourceを検索し、その結果を添えて調査を必ず一度提案する。既に提示または断られた同じ提案は繰り返さない。提案時は`create_research_campaign`を1回呼び、目的・対象Idea・範囲・試行数・期限を示す。この操作は調査を始めない。外部調査には利用者の明示許諾が必要であり、許諾snapshot・revision・期限・残試行数を確認した後だけ`approve_research_campaign`を呼ぶ。approveの成功結果に含まれるauthorization snapshot ID・revisionを調査Runの記録まで保持する。自動記録や提案への返答だけでは調査許諾にならない。
4. 許諾後の外部調査は同じChatGPT側で行い、通常のWeb検索とDeep Researchのどちらも同じ出典・Evidence保存契約を使う。開始前にapproveから返った許諾snapshot・revisionが現在も有効であることを確認し、試行数を超える追加調査や範囲変更は新たな許諾を得る。利用者が取消した場合は`revoke_research_campaign`で記録し、以後の調査を進めない。期限切れにも進まない。部分完了・失敗・中止を完了と偽らない。
5. 調査で実際に参照した公開資料ごとに、`capture_source`へ元のURL、資料タイトル、自分で作成した短い公開要約を保存する。公開メタデータをChatGPTへ返す必要がある場合は`egress_policy=shareable`を明示する。省略時の`local_only`を共有可能とみなさず、資料本文・抜粋・非公開URLを保存または返却しない。URL・タイトルを推測で作らない。
6. 保存済みの出典chunkが実際に取得できた場合だけ、`append_claim`でその資料が支えるClaimを作り、`capture_evidence`でClaimとそのchunkを結ぶ。後のChatGPT会話へ返す公開資料由来の短いClaimとEvidenceには、双方で`egress_policy=shareable`を明示する。非公開・機微な内容は`local_only`を維持し、章の共有根拠として使わない。資料やchunkが見つからない場合にEvidence IDを捏造しない。各操作の成功receiptからIDを受け取ってから次へ進む。`record_research_run`には実際の調査状態、approve済みのauthorization snapshot ID・revision、現行campaign revision、許諾時刻以後の開始・終了時刻を記録する。Runのsources欄だけでSourceやEvidenceが保存されたとは扱わない。
7. 完了した許諾済み調査について、0.エグゼクティブサマリー、1.ビジネスモデル、2.顧客とマーケットサイズ、3.収益モデル、4.競争優位性、5.実現可能性、6.リスク・撤退ライン、7.リスクミニマムなロードマップの全8章を整理する。外部根拠に依拠する章だけに実在IDを紐付け、全8章にEvidence IDを捏造しない。同じ資料のEvidenceは実際に支える複数章で再利用できる。`save_researched_idea_brief`は全8章の完成に加え、概要全体で少なくとも1件の現行・共有可能な出典Evidenceを必要とし、指定されたEvidence IDはすべて出典との現行関係を検証する。調査未実施・部分完了・有効な公開根拠が1件もない状態では正式調査済み概要にせず、必要に応じて`save_idea_brief`へ下書きを保存する。
8. 正式概要の保存が成功した後に`fetch_idea_brief`で最新版を取得し、内容から意味関係と分類を整理する。通常の整理は追加の承認を求めずに行う。意味関係は`link_entities`で保存する。既存の`search_facets`で分類語を照合し、必要な場合だけ`capture_facet`で分類語を作成して、`classify_entity`でIdea・Asset等を分類する。各分類・関係には、その判断を実際に支える共有可能なEvidence IDを指定する。Ideaを含む意味関係およびIdeaの分類には最新版の概要IDと該当章番号も指定する。`relate_facets`は根拠のある上位・下位分類だけに使い、根拠を取得できない関係・分類、循環する分類は作らない。事実と推測を分け、関係・分類は原則proposedまたはinferredとする。IdeaからAssetの再利用は`REUSES`、必要な能力は`REQUIRES_CAPABILITY`を使い、IdeaからAssetに`BASED_ON`を使わない。
9. 追加調査・訂正では最新の概要と関係revisionを再取得する。新しい概要を保存して影響する関係を再評価し、関係の訂正には直近関係の`supersedes_id`と現在の`expected_family_revision`を渡して同じ履歴を延長する。関係を撤回する場合は`retract_relation_assertion`で同じ後継履歴として記録する。削除や重複関係で訂正を表現しない。訂正後の検索で旧判断を現行として返さないことを確認してから、次の会話で現在の根拠付き関係を再利用する。期限・根拠・関係IDを推測しない。該当ツールが接続に無い場合は試作名を作らず、未反映と伝える。
