# Dotsへの自然な記録

この手順は、現在のメッセージでDotsが利用可能で、具体的なアイデアや資産の保存、既存アイデアを使った検討、調査結果の整理を求められた場合に使う。保存依頼で同じ未調査案が見つかった場合も、重複作成を避けたところで終了せず、手順3の一度の調査提案まで進む。一般論の質問、単なる雑談、第三者の噂だけでは記録を増やさない。単に一覧や検索結果を見たいだけの依頼には調査提案を追加しない。Dotsを選んでいないメッセージでDotsへ保存したと主張しない。

Dotsに新しく書く題名・要約・主張・分類語・事業評価は日本語を基本とする。固有名詞、資料の原題、URL、原文引用は改変せず、外国語の資料を要約するときも根拠の意味を変えない。保存形式の型名やツール引数は既存の契約どおりに使う。

正式概要の本文がChatGPTへの共有に適する場合は、保存操作で`egress_policy=shareable`を明示する。対象Ideaも共有可能な内容だけを`shareable`にする。既定の`local_only`で保存した概要は`fetch_idea_brief`では読み戻せない。機微な内容を無断で共有可に変えず、読み戻せない場合はグラフ登録を成功と報告しない。

1. 新しい具体的なIdeaが会話に出たら、Dots内で同一記録がないか先に確認する。同じ記録があれば重複作成せず既存記録を使い、新規の場合は`capture_idea`で未調査の下書きとして保存する。その後、関連する既存Idea・Asset・Sourceを検索する。類似するだけで同一とは断定しない。既に手元にある資料・能力・経験は`capture_asset`で独立して記録できる。本人が創業上の具体的な弱み、ためらい、障害を記録したいと述べた場合は、先に同一の懸念を検索し、未登録なら`capture_asset`の`kind=barrier`として日本語の短い題名と内容を保存する。単なる質問や一時的な分析観点を本人の弱みとして断定・捏造しない。再試行は同じ内容に同じ重複防止キーを使い、保存済みと伝えるのは書込み結果を受け取った後に限る。
2. 通常用のDotsでは、会話で共有した機微でないIdeaの短い題名・要約を`shareable`にし、会話原文はローカルに留める。人物の連絡先、非公開メモ、資料本文、非公開URLはChatGPTへ返さない。人物・組織・Idea・資料の共有設定は実際に共有可能な内容だけを明示する。架空fixture専用の接続先へ実データを書かない。曖昧な人物統合、削除、共有範囲の拡大には確認を得る。
   弱み・迷いは本人がChatGPTに共有した非機微な短い記述だけを`shareable`にできる。機微な詳細は既定の`local_only`を維持し、検索できなかったという理由だけで過去の不安がないと断言しない。新しい事業案を検討するときは共有可能な既存の弱み・迷いを検索し、同じ懸念があれば前回の記述と今回変わった前提を確認してから質問する。弱み・迷いを能力や強みとして`REUSES`に結び付けない。弱み・迷いだけの保存や閲覧では調査を提案しない。
3. 新規保存または既存記録の再利用で未調査Ideaを扱ったら、既存の会話内で同じIdeaへの調査提案を既に提示または断られていない限り、Dots内の関連Idea・Asset・Sourceを検索し、その結果を添えて調査を必ず一度提案する。既に提示または断られた同じ提案は繰り返さない。提案時は`create_research_campaign`を1回呼び、目的・対象Idea・範囲・試行数・期限を示す。この操作は調査を始めない。外部調査には利用者の明示許諾が必要であり、許諾snapshot・revision・期限・残試行数を確認した後だけ`approve_research_campaign`を呼ぶ。approveの成功結果に含まれるauthorization snapshot ID・revisionを調査Runの記録まで保持する。自動記録や提案への返答だけでは調査許諾にならない。
4. 許諾後の外部調査は同じChatGPT側で行い、通常のWeb検索とDeep Researchのどちらも同じ出典・Evidence保存契約を使う。開始前にapproveから返った許諾snapshot・revisionが現在も有効であることを確認し、試行数を超える追加調査や範囲変更は新たな許諾を得る。利用者が取消した場合は`revoke_research_campaign`で記録し、以後の調査を進めない。期限切れにも進まない。部分完了・失敗・中止を完了と偽らない。
5. 調査で実際に参照した公開資料ごとに、`capture_source`へ元のURL、資料タイトル、自分で作成した短い公開要約を保存する。公開メタデータをChatGPTへ返す必要がある場合は`egress_policy=shareable`を明示する。省略時の`local_only`を共有可能とみなさず、資料本文・抜粋・非公開URLを保存または返却しない。URL・タイトルを推測で作らない。
6. 保存済みの出典chunkが実際に取得できた場合だけ、`append_claim`でその資料が支えるClaimを作り、`capture_evidence`でClaimとそのchunkを結ぶ。後のChatGPT会話へ返す公開資料由来の短いClaimとEvidenceには、双方で`egress_policy=shareable`を明示する。非公開・機微な内容は`local_only`を維持し、章の共有根拠として使わない。資料やchunkが見つからない場合にEvidence IDを捏造しない。各操作の成功receiptからIDを受け取ってから次へ進む。`record_research_run`には実際の調査状態、approve済みのauthorization snapshot ID・revision、現行campaign revision、許諾時刻以後の開始・終了時刻を記録する。Runのsources欄だけでSourceやEvidenceが保存されたとは扱わない。
7. 完了した許諾済み調査について、エグゼクティブサマリー、ビジネスモデル、顧客とマーケットサイズ、収益モデル、競争優位性、実現可能性、リスク・撤退ライン、リスクミニマムなロードマップの全8章をMarkdownの完成稿として先に書く。見出し・本文・確認した出典URLを含め、表や図が理解を助ける箇所では使う。公開画像は実際に利用可能で適切なものだけを使い、写真・数値・図の根拠を創作しない。完成稿の全文を必ず`report_markdown`へ渡し、同じ`save_researched_idea_brief`の`sections`には8観点の検索・関係の根拠になる簡潔な内容とEvidence IDを渡す。両者を矛盾させず、本文だけまたは要約だけの保存にしない。画像URLは公開HTTPSだけを用い、秘密付きURLや任意のHTMLを含めない。外部根拠に依拠する章だけに実在IDを紐付け、全8章にEvidence IDを捏造しない。同じ資料のEvidenceは実際に支える複数章で再利用できる。正式保存には少なくとも1件の現行・共有可能な出典Evidenceが必要。調査未実施・部分完了・有効な公開根拠が1件もない状態では正式調査済み概要にせず、必要に応じて`save_idea_brief`へ下書きを保存する。
8. `save_researched_idea_brief`の成功結果を受け取ってから、対象Idea IDで`fetch_idea_brief`を呼び、返った最新版概要IDが保存結果と一致することと、保存されたMarkdown全文・8観点・出典IDを確認する。この確認前に意味グラフの登録へ進まない。確認した内容から、既存Idea・Asset等との意味関係と分類候補を選ぶ。通常の整理は追加の承認を求めずに行う。意味関係は`link_entities`で保存し、既存の`search_facets`で分類語を照合して必要な場合だけ`capture_facet`で作成し、`classify_entity`で分類する。各関係・分類には実際に支える現行・共有可能なEvidence ID、Ideaを含む場合は読み戻した最新版概要IDと該当章番号を指定する。`relate_facets`は根拠のある上位・下位分類だけに使い、根拠がない候補や単なる保存履歴を意味関係として作らない。事実と推測を分け、関係・分類は原則proposedまたはinferredとする。IdeaからAssetの再利用は`REUSES`、必要な能力は`REQUIRES_CAPABILITY`を使い、IdeaからAssetに`BASED_ON`を使わない。保存した関係・分類を読み戻して確認する。整理だけ失敗した場合はレポートを重複保存せず、レポートは保存済み・グラフは未完了と分けて伝える。
9. 追加調査・訂正では最新の概要と関係revisionを再取得する。新しい概要を保存して影響する関係を再評価し、関係の訂正には直近関係の`supersedes_id`と現在の`expected_family_revision`を渡して同じ履歴を延長する。関係を撤回する場合は`retract_relation_assertion`で同じ後継履歴として記録する。削除や重複関係で訂正を表現しない。訂正後の検索で旧判断を現行として返さないことを確認してから、次の会話で現在の根拠付き関係を再利用する。期限・根拠・関係IDを推測しない。該当ツールが接続に無い場合は試作名を作らず、未反映と伝える。
